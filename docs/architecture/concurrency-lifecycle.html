并行与生命周期 ​

HarnessVLN 的默认并行单位是完整 Task，不是 Task 内单步。并行策略同时受组件作用域、原生 资源限制和跨 Task 写入影响。

默认的单进程并行 ​

未配置 runner.devices 时，BenchmarkExecutor 使用容量为 task_parallelism * 2 的 asyncio 队列：producer 流式读取 benchmark.cases()， 多个 consumer 各自构造完整 stack 并调用 run_task。结果可能乱序完成，最后按输入 index 排序。

text
Benchmark.cases() -> bounded queue -> worker 0 -> whole Task A
                                  -> worker 1 -> whole Task B
                                  -> worker 2 -> whole Task C
1
2
3

该设计不会一次把百万级 split 全部装入内存，max_cases 也在 producer 侧截断。

Bench 级并行也有独立故障边界。一个 Bench 在构造、case stream 或调度前校验阶段失败时，App 将 异常收敛到该 BenchmarkSummary.error；同一 Run 中其他 Bench 不被取消。只有 Runner/Agent 配置解析、 进程取消或 Manifest 写入这类全局失败才结束整个套件调用。

配置驱动的 GPU 进程池 ​

配置 runner.devices 后，每个 GPU slot 对应一个 spawn 工作进程。Runner 在任何 Torch、Habitat 或模型代码加载前为子进程设置 CUDA_VISIBLE_DEVICES；组件配置继续使用逻辑 cuda:0 / gpu_device_id: 0，无需知道物理卡号。

yaml
runner:
  devices: [0, 1, 3, 4]
  workers_per_device: 1
  task_parallelism: 4
  bench_parallelism: 1
1
2
3
4
5

父进程先给每个 worker 一个完整 episode。某个 worker 完成后立即领取 case stream 中的下一个， 所以分配按真实耗时动态均衡，而不是预先静态切 split。每个 worker 内仍一次只运行一个完整 Task； session-scope VLN 在该 worker 的 case 之间复用 checkpoint。

终端输出也按进程边界隔离：父进程独占一条 tqdm 进度底行，worker 在导入 Habitat 或模型前就把 stdout/stderr 重定向到 Bench 自己的 logs/worker-*.log。进度只消费 worker 返回的结构化完成消息， 因此两个场景同时切换时也不会产生多条进度条或让原生日志插入其中。

多个 Bench 并发时共享同一个 DevicePool，每个 Bench 原子租用 task_parallelism 个 slot，不会分别 从 GPU 0 重新开始分配。workers_per_device 默认 1；显式增大表示主动让多个进程共享一张物理卡， Harness 不猜测显存容量。可用 slot 数为 len(devices) * workers_per_device，task_parallelism 不得超过它。

Task 内有哪些并发 ​

一个 Task 内存在协程并发，但控制权仍属于 Agent：

  • Agent.run 与 Environment.wait_terminal 同时等待；
  • VLN Job 可以作为后台协程或独立 worker 进程运行；
  • RPC worker 可发出异步反向 tool call；
  • ToolBus 允许只读调用并行，并追踪在途写调用；
  • Memory 由自身实现决定是否并行查询。

“Agent 与 VLN 同时运行”不意味着 Runner 分别调度它们。VLN 的生命周期由 navigator 管理， Agent 通过 Job 工具委托和观察状态。

session-scoped VLN 在 case 之间解除旧 ToolClient 绑定、释放 Job media，再绑定新环境；checkpoint 和 worker PID 保持不变。该 Bench session 结束后 ConfiguredStackFactory.close_session() 负责关闭。

两种串行约束 ​

同一 Bench 内的 task_parallelism 与 Runner 内的 bench_parallelism 不是同一个资源边界：

条件Task 并行Bench 并行原因
VLN scope: session，无设备池禁止可用每个 Bench 各有一个独立 worker，但同一 worker 不能绑定两个 Task
VLN scope: session，GPU 设备池可用可用每个 GPU 进程各有独立 navigator，进程内部仍串行
任一组件 serial: true禁止禁止表示进程级或外部共享资源独占
Memory writeback: true禁止禁止多实例会 read-modify-write 同一持久化文件

StackFactory 用 requires_serial 告诉 BenchmarkExecutor 是否允许多个 Task；另用 global_serial_reasons 告诉 App 是否允许多个 Bench。冲突在任何 Bench 构造前预检，错误会列出 具体 factory 与原因。Isaac Kit 是典型的 environment.serial 资源；Dummy Landmark Memory 会 报告 memory.serial / memory.writeback。

纯 session-scoped VLN 不自动禁止 Bench 并行，因为每个 Bench 会创建自己的 navigator/worker。 配置设备池时，物理 GPU 独占由 Runner 保证；仍会争用单例服务的组件应声明 serial: true。

扩展并行的正确方式

需要多个 Isaac case 并行时，使用多个隔离服务进程并让每个 Environment 独占连接；需要共享 Memory 并行写时，实现事务型存储并关闭单文件 writeback。不要只删除 serial 标记。

多频 VLN 如何保留 ​

DualVLN 一类大小脑不同频模型不由 Harness 拆开。一个 Job 在 worker 内维护 System 1、System 2、 帧窗口与连续轨迹；worker 可在需要时主动 nav.observe，推理后调用多个动作或 stand_still。 外部只看到 Job 状态与审计事件。

这意味着时间尺度分三层：

  1. Runner 的 Task 调度频率；
  2. Agent 的 workflow / Job 轮询频率；
  3. VLN 内部推理与原生 Environment tick 频率。

三层互不假定一一对应。Isaac 的一个 nav.move.discrete 还可能在中间件中推进最多数千 native tick， 直到高层动作完成。

交互会话为何串行 ​

env 模式没有 BenchmarkExecutor，但仍可能在交互 session 中复用 session-scoped VLN。公共 InteractiveNavigationSession.navigate() 因此使用会话级锁，把“构造 Task、运行 Agent、完成 清理”作为一个不可重叠操作；并发提交的指令按锁顺序执行。close() 使用同一把锁，所以不会在 Environment 仍运动或 VLN Job 仍活跃时关闭共享 worker。

这是会话级顺序，不是 Runner 逐步控制。每个 Task 内依然由 Agent 自主调用工具，批量 run 模式 的 Task/Bench 并行也不受这把锁影响。

取消不是简单 task.cancel() ​

取消时可能存在 GPU 进程、子进程组、文件映射和在途运动。现有实现使用：

  • shielded cancel/close，确保调用者被取消时清理仍能收敛；
  • worker process group 的 TERM/KILL 兜底与同步 fence；
  • Job seal，拒绝已关闭 Job 的新反向调用；
  • media release，按 Job 清理 file-backed array；
  • ToolBus write fence 与 drain；
  • 独立记录 cleanup error，不覆盖主异常。

编写新插件时，stop() 必须幂等、可在部分启动状态调用，并在返回前阻断后续副作用。

运行 Bench 与单环境任务 ​

CLI 有两个明确入口：run 调度评测套件，env 接收人工输入的导航指令。两者最后都把一个完整 Task 交给同一个 NavigationHarness，任务内部都由 Agent 主导。

批量评测 ​

bash
export PYTHONPATH="$PWD/src"
python -m harness.cli run \
  --runner config/runners/r2r_streamvln.yaml \
  --agent config/agents/passthrough_streamvln.yaml
1
2
3
4

Runner 配置引用一个或多个 Bench；每个 Bench 再引用自己的 Env。Agent 配置引用自己的 VLN 与 Memory，因此启动参数不会出现互相矛盾的 Bench/Env 或 Agent/VLN 组合。

退出码规则：所有 Task failure、case error、Bench error、cleanup error 和 output error 都为零时 返回 0，任一类非零返回 1。Runner/Agent 配置无法加载、Run 输出无法创建等全局错误直接抛出；单个 Bench 的构造、case 流或 session-scoped 清理失败写入该 Bench 结果，其他 Bench 仍会完成并共同产出 Manifest。

CLI 最后一行是本次唯一 Run 的 manifest.json 绝对路径。output.root 是父目录，不是会被下一次 运行覆盖的单个结果目录；详细 Episode、模块数据和视频沿 Manifest 中的相对路径读取。

在交互终端运行时，父进程只绘制一条 episode 进度条。所有 Bench 共享这条底行，GPU worker 完成完整 episode 后才向父进程递增一次；worker 的 Habitat/模型标准输出不会直接写终端。 R2R-CE 会从 split 文件给出精确总数，例如完整 val_unseen 显示 0/1839 到 1839/1839； 配置 max_cases 后以截断值为总数。stderr 不是终端（例如重定向到文件）时不绘制动态进度条。

多 GPU Runner ​

显卡分配写在 Runner 配置中，不需要命令行环境变量：

yaml
extends: r2r_janusvln.yaml
runner:
  devices: [0, 1]
  workers_per_device: 1
  task_parallelism: 2
output:
  root: runs/r2r_janusvln_2gpu

仓库提供 config/runners/r2r_janusvln_2gpu.yaml 作为可执行示例。两个进程分别把物理 GPU 0/1 映射成自己的逻辑设备 0，并动态领取完整 episode。模型 worker 是 GPU 工作进程的子进程，会继承 同一可见设备；Environment 也在该隔离进程中创建。每个 worker 的 stdout/stderr 写入该 Bench 的 logs/worker-<slot>-gpu-<device>.log，既保留 Habitat 场景切换诊断，也不会冲刷父进程进度条。

每行输入构造一个 NavTask 和 EnvironmentEpisode，然后调用一次 Agent.run(context)。CLI 只 提交指令、等待 Task 结束和显示结果，不代替 Agent 获取观测或执行动作。输入 quit / exit 退出 CLI；Agent 调用 nav.stop 只结束当前 Task。

基础版本每条指令创建新的 task-scoped Environment。若以后需要同一真机连接或仿真 session 跨 指令保持，应在 Environment 连接池/会话层扩展，不改变 Agent 工具协议。

InteractiveNavigationSession 是串行会话：并发调用 navigate() 时，后续指令等待前一完整 Task 及其清理结束；close() 也通过同一会话锁等待当前导航完成，再关闭 session-scoped VLN。关闭出现普通 错误时可以再次调用重试。该约束防止一个共享 VLN worker 同时绑定两个 Env。

Python API ​

python
import asyncio
from harness.app import execute_runner


async def main() -> None:
    run_summary, manifest = await execute_runner(
        "config/runners/dummy_passthrough.yaml",
        "config/agents/passthrough.yaml",
    )
    for benchmark in run_summary.benchmarks:
        print(benchmark.benchmark, len(benchmark.records))
    print(manifest)


asyncio.run(main())

并行语义 ​

  • bench_parallelism：同时运行多少个完整 Bench；
  • task_parallelism：一个 Bench 内同时运行多少个完整 Task；
  • devices：启用多进程模式并列出 Runner 可分配的物理 GPU；
  • workers_per_device：每张物理 GPU 的进程 slot 数，默认 1；
  • max_cases：每个 Bench 的 case 流截断；
  • case 的 stack/execution/score 异常写入 CaseRecord.error_stage/error，其他 case 继续；
  • score 异常或非法 MetricSet 保留已经完成的 NavigationResult，不会丢失 terminal、环境结果和 audit；
  • 非法 MetricSet 只清空当前 Case 的 metrics，不取消兄弟 Case，也不进入聚合；
  • Bench 构造或 case 流异常写入 BenchmarkSummary.error，其他 Bench 继续；
  • Bench 成功后的共享资源清理异常写入 BenchmarkSummary.cleanup_errors；
  • 每个 Bench 的结果按输入序号排序，而不是按完成先后；
  • 每个 Bench 完成后关闭它的 session-scoped VLN。

同一个 Task 内的 Agent、VLN worker 与 Environment 可以异步协作，但不由 Runner 分别调度。 多进程模式也只调度完整 Task；某个 worker 完成后才领取下一个 case。 serial: true 或持久化 Memory 出现在任一 stack 时，多 Bench 并行会在运行前失败；VLN 只有 scope: session 时则允许不同 Bench 各自创建 worker 并行。

普通任务与连续任务 ​

R2R/ObjectNav 的 case 通常只有一个 Goal。GOAT case 是单个多 Goal Task：

text
Bench emits one GOAT Case containing one compound Task
BenchmarkExecutor schedules that Case once
Agent -> Goal 0 -> goal.finish -> Goal 1 -> ... -> final Goal -> nav.stop
Environment remains alive for the whole Task

并行只发生在不同复合 Task 之间。Bench loader 保持 Goal 序列属于同一 Case，Executor 原样保留 该边界，因此不会破坏 GOAT 的连续位置与 Task 内记忆。
